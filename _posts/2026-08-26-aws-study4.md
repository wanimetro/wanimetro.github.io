# 06 Bedrock에서 모델 학습하기

지금까지는 Bedrock에서 제공하는 기본 모델을 그대로 호출하여 사용했다.

하지만 실제 서비스를 개발하다 보면 기본 모델만으로는 원하는 결과를 얻기 어려운 경우가 있다.

(특정 회사의 용어나 문체를 잘 따르는 모델이 필요하거나, 특정 분야의 데이터에 더 익숙한 모델이 필요한 경우 등)

이럴 때 기존 모델을 목적에 맞게 추가로 학습하여 \*\*사용자 지정 모델(Custom Model)\*\*을 만들 수 있다.

Amazon Bedrock에서는 대표적으로 \*\*미세조정(Fine-tuning)\*\*과 \*\*지속적인 사전 학습(Continued Pre-training)\*\*을 통해 모델을 사용자 목적에 맞게 조정할 수 있다.

## 6-1 미세조정과 지속적인 사전 학습

### 미세조정이란?

**미세조정**은 이미 사전 학습된 모델에 특정 작업이나 목적에 맞는 데이터를 추가로 학습시키는 방법이다.

예를 들어 고객 문의에 답변하는 AI를 만든다고 생각해보자.

기본 LLM도 질문에 답변할 수 있지만, 우리 서비스에서 원하는 **답변 형식이나 스타일, 특정 작업 수행 방식**까지 정확하게 따르지는 않을 수 있다.

이때 다음과 같은 입력과 원하는 출력의 예시를 이용해 모델을 미세조정할 수 있다.

```
사용자 질문
"배송은 얼마나 걸리나요?"

원하는 답변
"주문 완료 후 평균 2~3일 이내에 배송됩니다."

```

이와 같은 학습 데이터를 반복해서 제공하면 모델이 특정 작업에서 원하는 형태의 응답을 생성하도록 조정할 수 있다.

### 지속적인 사전 학습이란?

**지속적인 사전 학습**은 이미 사전 학습된 모델에 새로운 데이터를 추가로 학습시켜 기존 모델의 지식을 특정 도메인이나 데이터에 맞게 확장하는 방법이다.

예를 들어 일반적인 텍스트로 학습된 모델에 특정 산업 분야의 대규모 문서 데이터를 추가로 학습시키는 경우를 생각할 수 있다.

```
기존 Foundation Model
        ↓
특정 도메인의 대규모 데이터 추가 학습
        ↓
해당 도메인의 언어와 지식에 더 익숙한 모델

```

따라서 미세조정과 지속적인 사전 학습은 비슷해 보이지만 목적에서 차이가 있다.

미세조정→”\~ 이런 질문에는 \~이렇게  답해!”

지속적인 사전 학습→”\~ 분야의 데이터를 더 학습해!”

## 6-2 사용자 지정 모델 학습하기

이번에는 Bedrock에서 지원하는 사용자 지정 모델 학습 방식과 학습 데이터가 어떤 구조로 구성되는지 살펴본다.

크게 보면 다음과 같이 구분할 수 있다.

```
사용자 지정 모델 학습
│
├─ 미세조정 Fine-tuning
│    ├─ 텍스트 → 텍스트
│    ├─ 텍스트 → 이미지 / 이미지 → 임베딩
│    ├─ 단일 턴 메시지
│    └─ 다중 턴 메시지
│
└─ 지속적인 사전 학습
     └─ 텍스트 → 텍스트

```

### 학습 데이터 세트 형식

모델을 학습시키려면 먼저 학습에 사용할 데이터 세트가 필요하다.

이번에 살펴볼 데이터는 **JSONL(JSON Lines)** 형식으로 구성된다.

일반 JSON 형식: 여러 객체를 하나의 배열 안에 저장

```
[
  {"prompt":"안녕", "completion":"안녕하세요"},
  {"prompt":"고마워", "completion":"천만에요"}
]

```

JSONL 형식: 한 줄에 하나의 JSON 객체를 저장

```
{"prompt":"안녕","completion":"안녕하세요"}
{"prompt":"고마워","completion":"천만에요"}

```

학습 과정에서는 일반적으로 데이터를 **Training Data**와 **Validation Data**로 구분한다. (데이터 규모와 학습 목적에 따라 비율은 달라질 수 있음)

```
전체 데이터
   │
   ├── 80% → Training Data
   │          실제 모델 학습
   │
   └── 20% → Validation Data
              학습 결과 확인

```

### 미세조정 ① 텍스트 → 텍스트 생성

가장 기본적인 형태의 미세조정 방식

사용자의 입력인 `prompt`와 모델이 생성해야 하는 정답인 `completion`을 하나의 학습 데이터로 구성한다.

```
{
  "prompt": "<사용자 입력>",
  "completion": "<모델이 생성해야 하는 정답>"
}

```

특정 형식의 문서 요약, 질문 답변, 원하는 스타일의 텍스트 생성 등 **입력에 대해 원하는 출력 형태를 학습시키고 싶을 때** 활용할 수 있다.

예시

```
{
  "prompt": "새로 출시된 스마트폰의 카메라 기능을 강조하는 광고 문구를 작성해주세요.",
  "completion": "새로운 스마트폰의 카메라로 모든 순간을 선명하게 담아내세요."
}

```

이와 같은 `prompt → completion` 데이터를 여러 개 제공하면 모델이 입력에 대해 어떤 형태의 결과를 생성해야 하는지 학습하게 된다.

### 미세조정 ② 텍스트 → 이미지 / 이미지 → 임베딩 생성

Bedrock에서는  **이미지 생성이나 이미지 임베딩과 관련된 사용자 지정 학습**도 지원할 수 있다.

예를 들어 이미지와 해당 이미지를 설명하는 텍스트를 함께 학습 데이터로 구성할 수 있다.

```
{
  "image-ref":"s3://bucket/path/to/image.png",
  "caption":"<prompt text>"
}

```

`image-ref`는 실제 이미지가 있는 위치이고, `caption`은 그 이미지를 설명하는 텍스트

예시

```
{
  "image-ref":"s3://image-dataset/food/gourmet_pasta.png",
  "caption":"신선한 바질과 체리 토마토가 올려진 알 덴테로 조리된 스파게티 요리"
}

```

### 미세조정 ③ 단일 턴 메시지

**단일 턴**은 사용자와 AI가 한 번씩만 질문과 답변을 주고받는 형태이다.

데이터 구조

```
{
  "system":"<system message>",
  "messages": [
    {
      "role":"user",
      "content":"<user query>"
    },
    {
      "role":"assistant",
      "content":"<expected generated text>"
    }
  ]
}

```

- `system` → AI의 역할과 행동 방식
- `user` → 사용자의 질문
- `assistant` → 모델이 생성해야 하는 모범 답안

데이터 구조

```
System
"너는 TechCorp 고객 서비스 AI야."

User
"배터리 얼마나 가나요?"

Assistant
"일반적인 사용 시 최대 48시간입니다."

->

{
  "system":"당신은 TechCorp의 고객 서비스 AI 어시스턴트입니다. 항상 정중하고 도움이 되는 방식으로 고객의 질문에 대답해 주세요",
  "messages": [
    {
      "role":"user",
      "content":"TechCorp의 최신 스마트폰의 배터리 수명은 얼마나 가나요?"
    },
    {
      "role":"assistant",
      "content":"TechCorp의 최신 스마트폰 모델인 TC-X1의 배터리 수명은 일반적인 사용 시 최대 48시간 입니다."
    }
  ]
}

```

### 미세조정 ④ 다중 턴 메시지

**다중 턴**은 사용자와 AI의 대화가 여러 번 이어지는 형태이다.

단일 턴과 가장 큰 차이는 **이전 대화의 맥락까지 이어지는 대화 구조를 학습 데이터에 포함한다는 점**이다.

데이터 구조

```
User:
주식 투자를 시작하고 싶은데 어떻게 해야 해?

Assistant:
먼저 투자 목표를 정하고...

User:
ETF가 정확히 뭐야?

Assistant:
ETF는 Exchange Traded Fund의 약자로...

->

{
  "system":"당신은 FinanceWise 회사의 AI 재무 상담가입니다. 고객의 재무 상황을 이해하고 맞춤형 조언을 제공하세요.",
  "messages": [
    {
      "role":"user",
      "content":"주식 투자를 시작하고 싶은데, 어떻게 시작해야 할지 모르겠어요."
    },
    {
      "role":"assistant",
      "content":"초보자를 위한 몇 가지 조언을 드리겠습니다. 1. ~, 2. ~, 3. ~"
    },
    {
      "role":"user",
      "content":"ETF가 정확히 뭔가요?"
    },
    {
      "role":"assistant",
      "content":"ETF에 대해 자세히 설명해 드리겠습니다. ETF는 ~."
    },
    
  ]
}


```

## 6-3 외부 모델 가져오기

지금까지는 Bedrock에서 제공하는 기본 모델을 사용하거나, 기존 모델을 미세조정하여 사용자 지정 모델을 만드는 방법을 살펴보았다.

그런데 Bedrock에서는 이것뿐만 아니라 **외부에서 학습된 모델을 직접 가져와 사용할 수도 있다.**

예를 들어 Hugging Face에 공개된 모델이나 직접 학습한 모델을 Amazon S3에 업로드한 뒤, Bedrock으로 가져와 추론에 사용할 수 있다.

이번 실습에서는 Hugging Face에 공개된 **Meta Llama 3.2 3B Instruct** 모델을 로컬 환경에 다운로드한 뒤 Amazon S3에 업로드하고, 이를 Bedrock으로 가져와 실제로 실행해보았다.

전체 과정은 다음과 같다.

```
Hugging Face

↓

Llama 모델 다운로드

↓

Amazon S3에 모델 파일 업로드

↓

Bedrock에서 모델 가져오기

↓

Imported Model 생성

↓

Playground에서 모델 실행

```

### 1. Hugging Face 로그인

먼저 Hugging Face에 공개된 Llama 모델을 다운로드하기 위해 Hugging Face CLI 로그인을 진행했다.

PowerShell에서 다음 명령어를 실행했다.

```powershell
hf auth login

```

브라우저를 이용한 로그인을 선택하면 Hugging Face 인증 페이지가 열리고, 터미널에 표시된 코드를 입력하여 인증할 수 있다.

인증이 정상적으로 완료되면 다음과 같이 출력된다.

```
Token is valid.
Login successful.

```

이후 Hugging Face에 있는 모델을 CLI를 통해 다운로드할 수 있다.

### 2. Llama 3.2 3B Instruct 다운로드

다운로드 폴더로 이동한 뒤 다음 명령어를 실행했다.

```powershell
cd $HOME\Downloadhf download meta-llama/Llama-3.2-3B-Instruct --local-dir Llama-3.2-3B-Instruct

```

그리고 Hugging Face에서 Llama 3.2 3B Instruct 모델을 다운로드했다.

```powershell
hfdownloadmeta-llama/Llama-3.2-3B-Instruct--local-dirLlama-3.2-3B-Instruct

```

이 명령어를 실행하면 `Llama-3.2-3B-Instruct` 폴더가 생성되고 해당 폴더 안으로 모델에 필요한 파일들이 다운로드된다.

그런데 다운로드되는데 진짜 오래 걸렸다... 🫠

내 환경에서는 다운로드와 파일 재구성까지 거의 1시간 정도 걸렸다.

최종적으로 다음과 같이 완료되었다.

```powershell
Fetching 16 files: 100%
Download complete
Reconstruction complete: 100%
12.9GB / 12.9GB

```

모델 하나 받는데 용량이 약 13GB라니.….

### 3. 다운로드한 모델 파일 확인

다운로드가 끝난 후 `Llama-3.2-3B-Instruct` 폴더를 확인했다.

폴더에는 다음과 같은 파일들이 존재한다.

```
model-00001-of-00002.safetensors
model-00002-of-00002.safetensors
special_tokens_map.json
tokenizer.json
tokenizer_config.json
config.json
generation_config.json
model.safetensors.index.json

```

- `.safetensors` → 모델이 학습한 **가중치**가 저장된 파일
- `config.json` → 모델의 구조와 설정 정보
- `tokenizer.json`, `tokenizer_config.json` → 입력 텍스트를 모델이 처리할 수 있는 토큰으로 변환하기 위한 정보
- `generation_config.json` → 텍스트 생성과 관련된 기본 설정
- `model.safetensors.index.json` → 여러 개로 나누어진 모델 가중치 파일의 위치를 연결하는 인덱스

### 4. Amazon S3에 모델 업로드

이제 다운로드한 모델을 Amazon S3에 업로드한다.

Bedrock은 내 컴퓨터에 저장된 로컬 폴더에 직접 접근할 수 없기 때문에, 외부 모델을 가져오려면 먼저 **AWS에서 접근할 수 있는 위치에 모델 파일을 저장해야 한다.**

이번 실습에서는 Amazon S3를 이용했다.

Bedrock을 사용하고 있는 프랑크푸르트 리전인 `eu-central-1`에 S3 버킷을 생성하고, 앞에서 다운로드한 Llama 모델 파일을 업로드했다.
![](/assets/img/posts/aws/image1.png)


업로드가 완료되면 다음과 같이 모든 파일이 정상적으로 업로드된 것을 확인할 수 있다.

로컬 다운로드도 오래 걸렸는데 S3 업로드도 꽤 오래 걸렸다... 🫠

S3 업로드가 완료되었으므로 이제 실제로 모델을 Bedrock으로 가져온다.

### 오류 발생 : 첫 번째 모델 가져오기 실패

그런데 처음 모델 가져오기를 실행했을 때 `Failed`가 발생했다.

오류 내용을 확인해보니 다음과 같았다.

```
Amazon Bedrock could not find the expected file
(.../config.json).

Make sure the model is in Huggingface format
and that the file exists.

```

Bedrock이 지정한 S3 위치에서 `config.json` 파일을 찾지 못하고 있었다.

### 오류 원인

원인을 확인해보니 모델 다운로드가 완전히 끝나기 전에 다음 실습을 먼저 진행한 것이 문제였다.

앞에서 모델 다운로드에 거의 1시간이 걸리다 보니... 다운로드가 진행되는 동안 먼저 S3 업로드를 시도했었다. ^^

그 결과 필요한 모델 파일이 아직 모두 다운로드되지 않은 상태에서 S3에 파일을 업로드하게 되었고, `config.json`을 포함한 일부 파일이 누락되었다.

원인을 확인한 뒤 Hugging Face 모델 다운로드가 **완전히 끝난 것을 확인하고**, `config.json`, 모델 가중치, tokenizer 관련 파일 등 필요한 모델 파일을 다시 S3에 업로드했다.

이번 오류를 통해 외부 모델을 Bedrock으로 가져올 때는 단순히 **모델 가중치 파일만 업로드하면 되는 것이 아니라는 점**을 확인할 수 있었다.

Bedrock이 모델의 구조와 토크나이저 등을 파악할 수 있도록 **모델 가져오기에 필요한 Hugging Face 형식의 파일들이 S3 위치에 올바르게 존재해야 한다.**

필요한 모델 파일을 모두 S3에 업로드한 뒤 다시 `모델 가져오기`를 실행했다.

![모델 가져오기 성공](/assets/img/posts/aws/complete.png.png)

즉,

```

↓

Llama 3.2 3B Instruct 다운로드 ✓

↓

```

여기까지 완료했다.

### 6. Playground에서 가져온 모델 실행

가져오기가 완료된 모델은 Bedrock Playground에서 직접 테스트할 수 있다.

Playground를 열고 모드를 `단일 프롬프트`로 설정한 뒤 가져온 Llama 3.2 3B Instruct 모델을 사용했다.

이번 실습에서는 Llama의 프롬프트 형식에 맞춰 다음과 같은 프롬프트를 입력했다.

```
<|begin_of_text|><|start_header_id|>system<|end_header_id|>

Environment: ipython<|eot_id|><|start_header_id|>user<|end_header_id|>

Write code to check if number is prime, use that to see if the number 7 is prime<|eot_id|><|start_header_id|>assistant<|end_header_id|>

```

요청 내용 자체는 간단하다.

> 소수인지 확인하는 코드를 작성하고, 해당 코드를 이용해 숫자 7이 소수인지 확인해줘.

그런데 프롬프트를 보면 평소 LLM에게 질문할 때는 볼 수 없었던 문자열들이 포함되어 있다.

```
<|begin_of_text|>
<|start_header_id|>
<|end_header_id|>
<|eot_id|>

```

이들은 Llama가 메시지의 시작과 끝, 그리고 `system`, `user`, `assistant`와 같은 역할을 구분하기 위해 사용하는 특수 토큰이다.

즉, 우리가 일반적으로 Chat 형태의 LLM을 사용할 때 내부적으로 처리되는 메시지 구조를 이번 실습에서는 직접 프롬프트 형태로 구성한 것이다.

### **7. 가져온 모델 실행 확인**

잠시 기다린 뒤 Playground에서 동일한 프롬프트를 다시 실행하자 정상적으로 응답이 생성되었다.

Llama 3.2 3B Instruct 모델에 7이 소수인지 확인하는 Python 코드를 작성하도록 요청했고, 다음과 같이 `is_prime()` 함수를 생성했다.

```python
def is_prime(n):
    if n <= 1:
        return False

    if n == 2:
        return True

    if n % 2 == 0:
        return False

    max_divisor = int(n ** 0.5) + 1

    for d in range(3, max_divisor, 2):
        if n % d == 0:
            return False

    return True

print(is_prime(7))   //출력결과: True

```

이를 통해 Hugging Face에서 다운로드한 Llama 모델을 S3에 업로드하고, Bedrock으로 가져온 뒤 Playground에서 실제 추론까지 수행할 수 있음을 확인했다.

## 7-1 모델 호출 로깅

Bedrock의 **모델 호출 로깅** 기능을 사용하면 LLM 호출 시 발생하는 요청·응답 데이터와 관련 메타데이터를 기록할 수 있다.

이번 실습에서는 Bedrock의 모델 호출 로깅을 활성화한 뒤, Playground에서 직접 모델을 호출하고 **CloudWatch Logs에 호출 기록이 정상적으로 저장되는지 확인해보았다.**

```
CloudWatch Logs
        ↓
호출 기록 확인

```

## 7-2 Bedrock 대시보드 만들기

Bedrock을 실제 서비스에서 운영하다 보면 모델 호출과 관련된 데이터가 계속해서 쌓이게 된다.

하지만 수많은 로그를 하나씩 확인하면서 전체적인 서비스 상태를 파악하는 것은 쉽지 않다.

따라서 이번 실습에서는 **Amazon CloudWatch를 활용하여 Bedrock의 주요 지표를 한눈에 확인할 수 있는 대시보드**를 만들어보았다.

### CloudWatch란?

**Amazon CloudWatch**는 AWS 리소스와 애플리케이션의 상태를 모니터링할 수 있도록 **로그와 메트릭을 수집하고 시각화하는 서비스**이다.

Bedrock에서는 CloudWatch를 통해 모델 호출과 관련된 다양한 메트릭을 확인할 수 있다.

- 모델 호출 횟수
- 응답 시간(Latency)
- 입력 및 출력 토큰 수
- 호출 오류

앞선 실습에서 모델 호출 정보를 **로그로 기록하는 방법**을 알아보았다면, 이번에는 이러한 운영 지표를 **대시보드로 시각화하여 한눈에 확인하는 방법**을 실습해보았다.
![](/assets/img/posts/aws/image4.png)
CloudWatch 대시보드에 Bedrock의 주요 메트릭을 추가하여 모델의 호출량과 응답 상태 등을 한 화면에서 확인할 수 있는 모니터링 환경을 구성했다.

## 7-3 Bedrock Guardrails

생성형 AI의 답변은 항상 정확하거나 안전하다고 보장할 수 없다.

부적절한 콘텐츠가 생성되거나 개인정보와 같은 민감한 정보가 포함될 수 있기 때문에, 실제 서비스에서는 모델의 입력과 출력을 적절하게 제어하는 과정이 필요하다.

**→책임 있는 AI**의 중요성이 커지고 있으며, Amazon Bedrock에서는 이를 위한 **Guardrails** 기능을 제공한다.

### Bedrock Guardrails란?

**Amazon Bedrock Guardrails**는 사용자 입력과 모델의 응답에 미리 정의한 정책을 적용하여 부적절하거나 원하지 않는 콘텐츠를 필터링할 수 있는 기능이다.

주요 기능은 다음과 같다.

- **콘텐츠 필터**: 폭력, 모욕, 성적 콘텐츠, 증오 등의 유해 콘텐츠를 필터링
- **거부 주제**: 모델이 답변하지 않아야 하는 특정 주제를 정의
- **단어 필터**: 사용자 입력이나 모델 응답에서 특정 단어 및 표현을 필터링
- **민감 정보 필터**: 개인정보와 같은 민감한 정보를 감지하여 차단하거나 마스킹
- **Contextual Grounding Check**: 모델의 응답이 제공된 출처에 근거하고 있는지, 사용자의 질문과 관련된 답변인지 확인

특히 Contextual Grounding Check는 RAG와 같이 외부 데이터를 기반으로 답변을 생성하는 환경에서 **근거가 부족하거나 관련성이 낮은 응답을 제어하는 데 활용할 수 있다.**

이번 실습에서는 직접 Guardrail을 생성하고 모델에 적용하여 **설정한 정책에 따라 사용자 입력과 모델 응답이 어떻게 필터링되는지 확인해보았다.**
![](/assets/img/posts/aws/image5.png)

콘텐츠 필터가 적용된 상태에서 프롬프트에 욕설 shit을 포함하여 입력해보았다.

실행 결과, 입력한 프롬프트가 설정한 **콘텐츠 필터에 의해 감지되어 정상적인 모델 응답 대신 차단 메시지가 반환되는 것을 확인할 수 있었다.**

이를 통해 Guardrail이 모델의 답변을 생성한 이후에만 동작하는 것이 아니라, **사용자 입력 단계에서도 설정한 정책을 검사하여 부적절한 요청이 모델에 전달되는 것을 제한할 수 있음**을 확인했다.

즉, Bedrock Guardrails를 활용하면 애플리케이션 코드에서 모든 유해 표현을 직접 처리하지 않아도 Bedrock 수준에서 사용자 입력과 모델 응답에 대한 안전 정책을 적용할 수 있다.
