# 03 프롬프트 엔지니어링

## 3-1 프롬프트 엔지니어링 개념과 중요성

프롬프트는 LLM에게 전달하는 입력으로, 모델이 어떤 작업을 수행해야 하는지 알려주는 역할을 한다.

프롬프트 엔지니어링은 이러한 프롬프트를 설계하여 LLM이 원하는 방향으로 더 정확한 결과를 생성하도록 만드는 과정이다.

Amazon Bedrock 모델 중에서는 Anthropic의 Claude 모델이 한국어 답변 능력이 뛰어나다.

## 3-2 효과적인 프롬프트 작성 방법

프롬프트에는 단순한 질문뿐만 아니라 다양한 요소가 포함될 수 있다.

- LLM이 수행해야 하는 작업 또는 지시
- 답변에 필요한 정보와 맥락
- 원하는 출력의 예시
- 실제 입력 텍스트

이러한 요소를 어떻게 구성하는지에 따라 LLM의 출력 결과도 달라질 수 있다.

### 제로샷 프롬프팅 Zero-shot Prompting

Zero-shot Prompting은 별도의 예시를 제공하지 않고 모델에게 바로 작업을 지시하는 방식이다.

예를 들어,

```
다음 내용을 요약해줘.
```

라고 요청하면 모델은 별도의 예시 없이 사전 학습된 지식을 바탕으로 답변을 생성한다.

### 푸샷 프롬프팅 Few-shot Prompting

지시를 명확하게 작성하더라도 원하는 형태의 결과가 나오지 않을 수 있다.

이때 모델에게 몇 가지 예시를 함께 제공하면, 모델이 주어진 패턴과 맥락을 파악하여 비슷한 형태의 답변을 생성하도록 유도할 수 있다.

즉, Few-shot Prompting의 핵심은 **예시를 함께 제공하는 것**이다.


### 생각의 사슬 프롬프팅 Chain-of-Thought Prompting

복잡한 문제에서는 단순히 몇 가지 예시만 제공하는 것으로 충분하지 않을 수 있다.

생각의 사슬 프롬프팅은 복잡한 문제를 해결할 때 모델이 단계적인 추론 과정을 거치도록 유도하는 방식이다.

단순히 결과만 생성하도록 하는 것이 아니라 문제를 여러 단계로 나누어 처리하도록 만드는 방식이라고 이해했다.

## 3-3 Prompt Engineering with Claude
위 기법들은 일반적으로 적용 가능한 프롬프트 엔지니어링 기법들이다. 
다음으로 Anthropic Claude 모델을 효과적으로 활용하기 위한 프롬프트 작성 방법을 공부했다.

### 안내 프롬프트 Guided Prompt

Guided Prompt는 모델이 작업을 수행할 때 따라야 할 구체적인 단계를 프롬프트에 제시하는 방법이다.

앞에서 배운 푸샷 프롬프팅, 생각의 사슬 프롬프팅이랑 유사하다.

### 구조화된 프롬프트 Structured Prompt

Structured Prompt는 프롬프트 안에 포함된 정보의 역할을 명확하게 구분하는 방법이다.

Claude에서는 XML 태그를 이용해 프롬프트를 구조화할 수 있다.

예를 들어,

```xml
<thinking>
목차를 만들기 전에 어떤 내용이 필요한지 분석하세요.
</thinking>

<answer>
최종 목차를 작성하세요.
</answer>
```

처럼 각 부분의 역할을 구분할 수 있다.

이를 통해 프롬프트 내부의 여러 정보를 모델이 구분하기 쉽게 만들 수 있다.

### 시스템 프롬프트와 보안

프롬프트를 설계할 때는 모델의 성능뿐만 아니라 보안 문제도 고려해야 한다.

공부하면서 다음 두 가지 개념을 알게 되었다.

**Jailbreaks**

모델에 설정된 규칙이나 안전 기준을 우회하도록 프롬프트를 설계하는 공격이다.

**Prompt Leaking**

모델 내부에서 사용되는 시스템 프롬프트나 지시사항을 외부로 노출시키도록 유도하는 공격이다.

서비스에서 LLM을 사용할 경우 내부 프롬프트가 서비스 로직이나 중요한 정보를 포함할 수 있기 때문에 이러한 공격도 고려해야 한다.

# 04 Bedrock으로 RAG 구현하기

## 4-1 RAG 개념

RAG(Retrieval-Augmented Generation, 검색 증강 생성)는 LLM이 답변을 생성하기 전에 외부의 지식 저장소에서 관련 정보를 검색하고, 해당 정보를 함께 참고하여 답변을 생성하는 방식이다.

일반적인 LLM의 답변 과정은 다음과 같다.

```
질문
 ↓
LLM
 ↓
답변
```

RAG에서는 중간에 **검색 과정**이 추가된다.

```
사용자 질문
     ↓
관련 자료 검색
     ↓
관련 자료 + 사용자 질문
     ↓
LLM
     ↓
답변
```

RAG에서는 문서와 사용자 질문을 Embedding을 통해 Vector로 변환한 뒤, 의미적 유사도를 비교하여 질문과 관련된 문서를 검색한다.

추가로 [AWS 공식 문서 - Retrieval Augmented Generation](https://docs.aws.amazon.com/sagemaker/latest/dg/jumpstart-foundation-models-customize-rag.html)를 참고해 RAG에 대해 더 공부했다.

여기서 **임베딩(Embedding)** 개념에 대해 더 명확히 짚고 넘어갈 수 있었다.

### Embedding

Embedding은 쉽게 말하면 텍스트의 의미를 컴퓨터가 비교할 수 있는 숫자 벡터로 변환하는 과정이다.

예를 들어,

```
"고양이"
   ↓
[0.82, 0.12, 0.91, 0.35 ...]
```

```
"강아지"
   ↓
[0.79, 0.18, 0.88, 0.31 ...]
```

처럼 텍스트를 숫자의 배열인 Vector로 변환한다.

의미적으로 비슷한 텍스트는 Vector 공간에서도 서로 가까운 위치에 표현될 수 있다.

따라서 RAG에서는 문서뿐만 아니라 사용자의 질문도 Embedding한다.

```
사용자 질문
      ↓
Embedding Model
      ↓
Query Vector
```

문서 역시 미리 Embedding하여 Vector Database에 저장한다.

```
문서
 ↓
Embedding Model
 ↓
Vector
 ↓
Vector Database
```

사용자가 질문하면 질문 Vector와 저장되어 있는 문서 Vector를 비교하여 의미적으로 관련된 문서를 찾는다.

전체 과정을 정리하면 다음과 같다.

```
              [사전 준비]

PDF / DB / 웹 문서
        ↓
      Chunking
        ↓
  Embedding Model
        ↓
      Vector
        ↓
 Vector Database


              [질문 발생]

사용자 질문
        ↓
  Embedding Model
        ↓
   Query Vector
        ↓
Vector Database 검색
        ↓
 관련 문서 검색
        ↓
질문 + 검색된 문서
        ↓
       LLM
        ↓
     최종 답변
```

## 4-2 Vector Database

Vector Database는 텍스트, 이미지, 오디오 등의 데이터를 Vector 형태로 저장하고 검색하기 위한 데이터베이스이다.

Embedding을 통해 데이터가 Vector로 변환되면 Vector Database에 저장할 수 있다.

사용자의 질문 역시 Vector로 변환한 뒤 저장되어 있는 Vector와 비교하여 가까운 데이터를 찾는다.

이번 실습에서는 AWS에서 사용할 수 있는 Vector Database 중 **Aurora PostgreSQL + pgvector**를 사용했다.

```
Embedding
    ↓
Vector
    ↓
Aurora PostgreSQL
    +
 pgvector
```

# 4-3 LangChain으로 RAG 직접 구현하기

이번 실습에서는 **Amazon Bedrock + LangChain + Aurora PostgreSQL + pgvector**를 이용해 RAG의 구성 요소를 직접 연결해봤다.

## 1. 필요한 패키지 준비

책에서는 다음과 같이 pipenv를 이용해 필요한 패키지를 설치한다.

```bash
pipenv install langchain-aws langchain langchain-community bs4
```

실습 과정에서는 LangChain뿐만 아니라 PostgreSQL과 pgvector를 사용하기 위한 패키지도 필요했다.

처음 `pipenv` 명령어를 실행했을 때 다음과 같은 오류가 발생했다.

```
pipenv : 'pipenv' 용어가 cmdlet, 함수, 스크립트 파일 또는
실행할 수 있는 프로그램 이름으로 인식되지 않습니다.
```

이전에 만들어둔 `bedrock-study` 가상환경이 있었기 때문에 해당 Python 환경을 이용해 필요한 패키지를 설치하고 실습을 계속 진행했다.


## 2. AWS 공식 문서 불러오기

RAG가 참고할 외부 지식으로 Amazon Titan Text Embeddings 공식 문서를 사용했다.

```python
from langchain_community.document_loaders import WebBaseLoader

loader = WebBaseLoader(
    "https://docs.aws.amazon.com/bedrock/latest/userguide/titan-embedding-models.html"
)

docs = loader.load()
```

`WebBaseLoader`를 이용해 AWS 공식 웹페이지를 LangChain에서 사용할 수 있는 Document 형태로 불러왔다.

실행 결과,

```
불러온 문서 개수: 1
```

이 출력되었다.

즉,

```
AWS Documentation
        ↓
  WebBaseLoader
        ↓
LangChain Document
```

과정이 정상적으로 동작했다.

## 3. 문서를 Chunk로 나누기

불러온 웹 문서를 그대로 사용하는 대신 작은 단위로 나눴다.

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,
    chunk_overlap=200
)

splits = text_splitter.split_documents(docs)
```

실행 결과,

```
Chunk 개수: 6
```

이 출력되었다.

이번 실습에서는 `chunk_size=1000`, `chunk_overlap=200`으로 설정했다.

문서를 여러 개의 Chunk로 나눈 뒤 이후 각각의 Chunk를 Embedding하여 Vector Database에 저장하게 된다.

```
AWS 공식 문서
      ↓
  Chunking
      ↓
Chunk 1
Chunk 2
Chunk 3
...
Chunk 6
```

## 4. Titan Text Embeddings V2 사용하기

Chunk를 Vector로 변환하기 위해 Amazon Bedrock의 **Titan Text Embeddings V2**를 사용했다.

```python
from langchain_aws import BedrockEmbeddings

embeddings = BedrockEmbeddings(
    model_id="amazon.titan-embed-text-v2:0",
    region_name="eu-north-1"
)
```

Embedding이 실제로 어떤 결과를 만드는지 확인하기 위해 질문 하나를 직접 Vector로 변환해봤다.

```python
test_vector = embeddings.embed_query(
    "Titan Text Embeddings V2는 몇 차원인가요?"
)

print("임베딩 차원:", len(test_vector))
print("벡터 앞 5개:", test_vector[:5])
```

실행 결과,

```
임베딩 차원: 1024

벡터 앞 5개:
[-0.011190625838935375,
 0.013417812064290047,
 0.030738433822989464,
 0.027474893257021904,
 0.008042377419769764]
```

가 출력되었다.

즉 실제로

```
"Titan Text Embeddings V2는 몇 차원인가요?"
                    ↓
         Titan Embeddings V2
                    ↓
[-0.0111, 0.0134, 0.0307, ...]
                    ↓
             1024 dimensions
```

과정이 이루어지는 것을 확인했다.

책에서 계속 등장했던 **텍스트를 Vector로 변환한다**는 개념을 실제 숫자로 확인할 수 있었다.

## 5. Aurora PostgreSQL + pgvector 구성

다음으로 생성한 Vector를 저장할 Vector Database가 필요했다.

이번 실습에서는 AWS RDS에서 **Aurora PostgreSQL**을 생성하고 `pgvector` 확장을 사용하는 방식으로 구성했다.

```
Aurora PostgreSQL
       +
    pgvector
       ↓
Vector 저장 및 검색
```

DB 클러스터 식별자는 다음과 같이 설정했다.

```
pgvector
```

마스터 사용자 이름은

```
postgres
```

로 설정했다.

인스턴스는 **Aurora Serverless**를 사용했고 실습용으로 다음과 같이 설정했다.

```
최소 용량: 0 ACU
최대 용량: 4 ACU
비활성 상태 후 일시 중지: 5분
```

보안 그룹은

```
pgvector-sg
```

로 생성했고 PostgreSQL 기본 포트인 `5432`를 사용했다.

DB 생성이 완료된 뒤 RDS의 **연결 및 보안** 메뉴에서 클러스터 Endpoint를 확인했다.

![Aurora PostgreSQL Endpoint](/assets/img/posts/aws/endpoint.png)

Reader Endpoint와 Writer Endpoint가 함께 생성되어 있는 것을 확인했다!!

이번 실습에서는 Vector를 데이터베이스에 저장해야 했기 때문에 **Writer Endpoint를 Python의 PostgreSQL 연결 정보에 사용했다.**

```
Python
   ↓
Writer Endpoint
   ↓
Aurora PostgreSQL
```

그리고 로컬 PC에서 Aurora PostgreSQL의 `5432` 포트에 접근할 수 있는지 확인했다.

```powershell
Test-NetConnection [Writer Endpoint] -Port 5432
```

실행 결과,

```
TcpTestSucceeded : True
```

가 출력되었다.

즉 Windows 환경에서 AWS의 Aurora PostgreSQL까지 네트워크 연결이 가능한 상태임을 확인했다.

## 6. PostgreSQL 연결 확인

Python에서 Aurora PostgreSQL에 연결한 뒤 pgvector extension의 버전을 확인했다.

실행 결과,

```

```

이 출력되었다.

즉,

```

       ↓

pgvector
```

까지 연결이 정상적으로 이루어진 것을 확인했다.

이 과정에서 각 Chunk가 Titan Text Embeddings V2를 통해 Vector로 변환되고 pgvector에 저장된다.

```

      ↓

      ↓

      ↓

```

실행 결과,

```

```

가 출력되었다.

여기까지 진행하면서

```

 ↓
WebBaseLoader
 ↓
Chunking

Embedding

 ↓
Aurora PostgreSQL + pgvector
```

라는 RAG의 문서 저장 과정을 직접 실행했다.

## 8. Vector DB에서 관련 문서 검색

Vector DB 저장이 완료된 뒤 다음 질문을 이용해 관련 문서를 검색했다.

```
Titan Text Embeddings V2는 몇 차원인가요?
```

실행 결과 실제로 Vector Database에 저장된 문서 중 질문과 관련된 Chunk들이 출력되었다.

```
===== 검색된 문서 =====

--- 검색 결과 1 ---

Model ID – amazon.titan-embed-text-v2:0
Max input text tokens – 8,192
Max input text characters – 50,000
...
Output vector size – 1,024 (default), 512, 256
...

--- 검색 결과 2 ---

Model ID – amazon.titan-embed-text-v2:0
...
Output vector size – 1,024 (default), 512, 256
...

--- 검색 결과 3 ---

...
outputs a vector of 1,024 dimensions.
...
```

앞에서 웹페이지 전체를 6개의 Chunk로 나누고 Embedding하여 저장했는데, 질문을 입력하자 그중 질문과 관련된 Chunk가 검색되는 것을 직접 확인할 수 있었다.

이 단계에서는 아직 최종 답변을 생성한 것이 아니라 **Vector DB에서 관련 문서를 검색한 상태**이다.

```
질문
 ↓
Embedding
 ↓
Vector DB 검색
 ↓
관련 Chunk 반환
```

## 9. 검색된 문서를 이용해 최종 답변 생성

Vector DB 검색까지 정상적으로 동작한 뒤, 검색한 문서를 LLM에게 전달하여 최종 답변을 생성하도록 했다.

최종적으로 다음 질문을 입력했다.

```
Titan Embedding V2는 몇 차원인가요?
```

검색된 AWS 공식 문서를 Context로 전달한 뒤 모델이 생성한 결과는 다음과 같았다.

```
===== RAG 최종 답변 =====

Amazon Titan Text Embeddings v2 모델은 기본적으로
1,024 차원의 벡터를 출력합니다.

이 벡터는 문서, 단락, 문장의 의미적 표현을
생성하는 데 사용할 수 있습니다.
```

최종적으로

```
사용자 질문
      ↓
Embedding
      ↓
Vector DB 검색
      ↓
관련 AWS 문서 검색
      ↓
검색된 문서 + 질문
      ↓
LLM
      ↓
최종 답변
```

과정까지 실행되는 것을 확인했다.

실습 결과를 한 번에 확인하면 다음과 같다.

```
불러온 문서 개수: 1
Chunk 개수: 6
임베딩 차원: 1024
pgvector 버전: 0.8.0
PostgreSQL 연결 성공!
Vector DB 저장 완료!
```

이후 관련 문서 검색과 최종 답변 생성까지 정상적으로 실행되었다.

# 실습 중 발생한 문제와 해결🫠

## Claude Sonnet 4.5 Model Identifier 오류

책에서는 Claude 3.5 Sonnet을 사용했지만 현재 Bedrock 환경에 맞춰 Claude Sonnet 4.5를 사용하려고 했다.

처음 모델을 호출하는 과정에서 다음 오류가 발생했다.🥲

```
ValidationException:
The provided model identifier is invalid.
```

Bedrock에서 확인한 결과 현재 사용하려는 Claude Sonnet 4.5는 Cross-region inference를 통해 호출해야 했고 EU Inference Profile을 사용했다.

```python
llm = ChatBedrockConverse(
    model="eu.anthropic.claude-sonnet-4-5-20250929-v1:0",
    region_name="eu-north-1"
)
```

이를 통해 Bedrock에서 모델을 사용할 때는 단순히 Foundation Model의 Model ID만 확인하는 것이 아니라 **현재 모델의 호출 방식과 Inference Profile도 확인해야 한다는 점**을 알게 되었다.

## Claude Sonnet 4.5 호출 과정의 결제 수단 오류

Inference Profile을 수정한 뒤 다시 Claude Sonnet 4.5를 호출했지만 이번에는 다음 오류가 발생했다.🥲

```
AccessDeniedException:

Model access is denied due to
INVALID_PAYMENT_INSTRUMENT

A valid payment instrument must be provided.
```

오류 메시지에서 `INVALID_PAYMENT_INSTRUMENT`가 출력되었고 Claude 모델의 사용 과정에서 결제 수단과 관련된 문제가 발생한 것을 확인했다.

따라서 이후 실습에서는 Claude 대신 Amazon Nova 모델로 변경하여 RAG의 최종 LLM 호출을 진행했다.(돈 이슈💸💸)

# 오늘 실습 정리

이번 실습을 통해 RAG의 전체 흐름을 코드와 AWS 서비스를 이용해 직접 확인했다.

```
AWS 공식 문서
      ↓
WebBaseLoader
      ↓
Chunking
      ↓
Titan Text Embeddings V2
      ↓
1024차원 Vector
      ↓
Aurora PostgreSQL + pgvector
      ↓
관련 문서 검색
      ↓
검색된 문서 + 사용자 질문
      ↓
LLM
      ↓
최종 답변
```

특히 이전에는 RAG를 단순히 **LLM이 외부 문서를 참고해서 답변하는 방식** 정도로 이해했는데, 이번 실습에서는 문서를 불러오고, Chunk로 나누고, Embedding하고, Vector DB에 저장한 뒤 다시 검색하는 과정을 하나씩 직접 실행해볼 수 있었다.

또한

```
텍스트 → Embedding → Vector
```

과정을 실제 `1024`개의 숫자로 확인했고, 해당 Vector들이 pgvector에 저장되어 질문과 관련된 문서를 검색하는 과정까지 확인했다.
